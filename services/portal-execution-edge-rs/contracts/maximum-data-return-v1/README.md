# Portal Execution maximum-data return pack v1

This is an additive, machine-readable return pack for
`PORTAL_EXECUTION_EDGE_MAXIMUM_DATA_DISCOVERY_PUBLICATION_AND_RETURN_REQUEST_v1.md`.
It is contract evidence only: it contains no database credential, business row,
raw payload, SQL selector, Redis inspection, browser route, listener, command
port or runtime activation.

## E3 complete

`e3-coverage.manifest.json` locks the E3 source coverage result:

- 23 current Screen-BFF contracts and all 22 required demand surfaces;
- 126 field-level mappings across 34 reusable field definitions;
- 12 action capability records and 10 derived-metric feasibility rulings;
- 14 downstream work orders that name source operation, resource identity,
  continuation, reducer, empty/stale/gap behavior, owner and next action;
- eight no-business-row fixtures covering populated, empty, partial, stale,
  gap, duplicate, correction and next-page consumer semantics;
- zero unmapped required frontend fields and zero unmapped execution actions.

The three required CSVs are generated by the validated Rust
`maximum-data-contract` crate. `PORTAL_DOWNSTREAM_WORK_ORDERS.csv` is the
fourth E3 handoff artifact required by the governing plan. Do not hand-edit a
CSV: change the JSON registry, pass the Rust/TypeScript tests, then regenerate
it with `render_e3`.

The exact Manager-v2 upstream bound is 200 rows and 1 MiB per source request.
That is a frame/page bound, never a total-history cap. No E3 entry grants
generic relation, SQL or direct-DB access. Existing but unqualified read
shapes remain `EXISTS_BUT_NOT_SAFE_TO_EXPOSE`; genuine source absence remains
`OWNER_ACTION_REQUIRED` with a named owner. In particular, current orders and
positions are not mislabeled as replay, and no Trading-System command is
represented as active.
