### 2.3 Certificates and secrets (design, decisions for the owner)
- Edge server certificate (Control API to Edge, 10.70.0.2): the existing `edge-server.crt/.key` in the shared Edge directory name the IP, not the port, so the new instance REUSES them by mounting the same directory read-only like the other three (no copy, no new custody). JWKS (`control-api.jwks.json`, the same Control API signer keys), `sgp-client-ca.crt` (client CA bundle), `source-proxy-ca.crt`, `source-proxy-client.pem`, `source-proxy-admission-token`: same files, same directory. A separate secrets directory (copy by name of those seven files) is possible but adds copies of a private key and an admission token; recommended only if the owner wants per-profile revocation. New things in the shared directory: none.
- Proxy server certificate (Edge to proxy, 172.30.0.1): a NEW leaf `source-proxy-server-okx.crt/.key` placed NEXT to the existing files (they stay byte-identical, so the three running proxies are untouched). Key generated by `cert-csr` as root inside `/srv/primus/portal/source-proxy` (P-256, mode 0640 root:portal-runtime, never leaves the host); CSR (public) written to the staging dir; the owner signs it with the CA that issued the existing proxy certificate (the Edge trusts `source-proxy-ca.crt`; the evidence names the family "Primus Portal Execution Offline Root v1": whether the signer key is on this host or offline is unverified, hence a CSR flow). SAN must contain `IP:172.30.0.1` (the Edge verifies by address) and, to match the existing certificate, `URI:spiffe://primusspark/portal/source-proxy/execution`; EKU serverAuth. Validity: not longer than the existing proxy leaf (its notAfter is unverified: read it, see 5); `cert-install` refuses a certificate that does not chain to `source-proxy-ca.crt`, does not match the generated key, lacks the IP SAN or serverAuth, or expires within 30 days.
- Alternative without a new certificate (not drafted): listen on a new port of an existing bridge gateway (for example 172.23.0.1:8445) and attach the new Edge to the Paper bridge. Rejected as default: it puts a second profile on the Paper network and still needs the Paper nginx file untouched; mentioned for the owner's choice.
- Client side of the proxy: the Edge presents `source-proxy-client.pem`, verified against `projection-ingestor-ca.crt` (template `ssl_client_certificate`): the same file as the other Edges, no new identity. Manager side: the proxy presents the existing `manager-v2-client.pem` to the OKX Manager (the OKX Manager expects the same client subject, TS plan section 6).
- nginx file: rendered from the repo template; whether the Paper/Sandbox proxies append extension location sets (`eds11r-r4-r5`, `market-data-layer-v1`, see `execution-d2-render-source-proxy.sh`) is unverified, so the OKX route file carries ONLY the Manager read routes. ### 2.4 Order (each step its own owner approval with hashes; Core baseline and OK first, silence is not an OK)

5. `verify` (read-only) and `edge-tls`. Then (not in this script) guard pin override and Core's slot, each its own step.
Rollback: `rollback` = `compose down --remove-orphans` for project `portal-execution-edge-okx` only (containers + bridge); `rollback-files` (SUDO 5) removes only the four `*okx*` files. The three running stacks, the OKX Managers, the shared Edge directory and every existing proxy file are never modified.
